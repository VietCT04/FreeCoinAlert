# User Stories

## Purpose

User stories are approved requirements and planning artifacts. They describe stakeholder outcomes, not proof that every criterion is implemented.

Follow-up GitHub issues and their approved comments control implementation scope. Current availability belongs in the authoritative domain documents listed in the [Documentation Guide](../README.md), not in historical stories. Keep a story unchanged unless its requirement itself is corrected.

## Naming

Store stories here as `US-0001-short-title.md`. Numbers are sequential and never reused.

## Story Workflow

1. Propose and obtain approval for a stakeholder-focused story.
2. Create focused GitHub issues linked to that story.
3. Obtain approval for each issue's technical solution in its GitHub thread.
4. Implement approved issues in focused pull requests.

Read [PRODUCT.md](../PRODUCT.md), [SECURITY.md](../SECURITY.md), the relevant domain document, and [CONCERNS.md](../CONCERNS.md) when shaping requirements.
